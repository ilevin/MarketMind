## Context

当前 v0.2.0 已有 `app_user`、Session、Argon2id 密码哈希、用户创建服务和管理员 API。全新安装以及从 v0.1.0 升级时，迁移 `0002_multi_user_auth` 都可能写入一个用户名为 `admin`、密码为不可登录占位值的 legacy owner；现状要求服务启动前由运维通过 CLI 设置密码。

本变更需要跨越页面路由、认证 API、用户服务、数据库写入锁、CSRF 中间件、模板/前端和部署文档。DuckDB 采用单写者模型，且旧数据已归属 legacy owner，因此初始化必须既能安全处理并发首访，也不能为升级库创建第二个孤立账户。

## Goals / Non-Goals

**Goals:**

- 在首次访问时提供匿名可达的初始化页面和首用户创建流程。
- 让首用户自动成为启用状态的 `admin`，创建成功后立即建立 Session。
- 在全新空库和仅含迁移占位账户的升级库中工作；升级库的自选、指数配置和标签继续归属同一用户。
- 通过写锁内二次检查保证初始化只能成功一次，并复用现有用户名/密码校验和 Argon2id 哈希策略。
- 初始化完成后关闭匿名入口，保持现有登录、CSRF、管理员授权和公开注册关闭策略。
- 保留 CLI 作为服务不可访问或运维自动化场景的后备初始化/密码管理方式，并更新部署文档。

**Non-Goals:**

- 不开放常规匿名注册，不允许首用户流程创建第二个或普通角色账户。
- 不改变既有 Session Cookie 格式、用户数据隔离模型、登录限速策略或管理员用户管理 API。
- 不删除 `must_change_password` 字段，也不在本变更中重新设计密码强制修改页面。
- 不改变数据库迁移的历史版本；初始化逻辑在应用服务层兼容现有占位 legacy owner。

## Decisions

### 1. 用占位密码识别未初始化状态

系统将以下状态视为未初始化：`app_user` 没有记录，或仅有一个由迁移写入的 `PLACEHOLDER_HASH` 账户且该账户仍为启用管理员、没有其他用户。提交首用户时：空库创建新行；占位账户则在同一写事务内更新用户名、密码哈希和初始化标志，保留其 `user_id` 及已迁移的私有数据。

选择应用层状态识别而不是新增 schema 字段，是因为现有迁移已经有明确的不可登录占位哈希，且不需要为历史数据库增加另一条迁移。检测逻辑必须集中在 UserService/仓储中，避免页面和 API 各自解释状态。

### 2. 新增独立的匿名初始化页面和 API

增加 `/setup` 页面及 `POST /api/auth/setup`。表单使用用户名、密码和密码确认；服务端只接收并校验用户名和密码，密码确认由 API schema 或服务层验证。成功响应创建与登录相同安全属性的 Session Cookie，返回首用户基本信息。

登录页在未初始化状态下重定向到 `/setup`；初始化完成后 `/setup` 重定向到 `/login` 或返回 409，不能继续显示可提交的匿名创建表单。私有业务 API 的既有 401 语义保持不变；页面入口负责将用户引导到初始化页面，避免把所有 API 的认证错误合同改成新的状态码。

### 3. 初始化写入采用“哈希锁外、状态锁内二次检查”

先在写锁外计算 Argon2id 哈希，再进入 `write_coordinator.write()`，重新读取初始化状态并执行创建或认领。只有二次检查仍显示未初始化时才提交；另一个请求已完成时返回明确的 409。首用户创建、占位账户更新和 Session 创建必须处于同一数据库写事务语义内，避免产生无密码账户或无效 Session。

### 4. 初始化接口豁免 CSRF，但增加限速和最小暴露面

初始化发生在没有 Session 的匿名状态，因此与登录一样不要求 CSRF Token，并显式加入 CSRF 豁免路径。入口只在未初始化时可用，不能通过该 API 指定 role、is_active 或用户 ID。为防止公开端点被密码猜测/资源消耗，初始化请求复用进程内按 IP 的限速器，并对错误只返回可展示的校验信息，不记录密码、Token 或密码哈希。

### 5. 保留 CLI 兼容和回滚路径

CLI `users set-password`、`users create`、`users promote` 保留，用于无法从浏览器访问服务的部署、自动化以及紧急恢复。文档将全新部署的首选路径改为启动服务后访问 `/setup`；升级库也可通过首访认领占位 owner，CLI 仍作为后备路径。若发布后需要回滚应用代码，旧代码看到已设置的真实密码账户时仍可正常登录；旧代码不会重新开放初始化入口。

## Risks / Trade-offs

- [匿名首用户接口暴露在网络上] → 仅在占位/空用户状态开放，成功后立即关闭；对 IP 限速；部署文档要求在可信网络完成初始化并尽快配置 HTTPS。
- [两个首访请求并发导致重复用户] → 写锁内重新读取状态并在同一事务中创建/认领，失败请求返回 409；增加并发集成测试。
- [升级库被未知访问者先认领管理员] → 升级文档明确服务应先在受控网络启动并完成初始化；占位 owner 只有在仍处于未初始化状态才可认领，任何真实密码账户存在时都不会开放匿名入口。
- [保留 legacy owner 的用户名/数据映射与改名复杂] → 认领占位账户而不是新增账户，复用现有 `user_id` 和所有外键；对用户名查重进行写锁内检查。
- [应用运行时与 CLI 同时写 DuckDB] → 继续遵守单写者约束；CLI 文档和现有锁冲突提示不变，首访流程由运行中的应用自身完成。
- [初始化密码哈希耗时造成重复提交] → 前端禁用重复提交按钮，服务端仍以限速和写锁保证正确性；哈希失败或数据库异常不得创建半成品用户。

## Migration Plan

1. 发布应用代码和测试，数据库沿用现有 `0002_multi_user_auth`，不新增历史迁移。
2. 全新部署按 `alembic upgrade head` 后启动服务，浏览器访问 `/` 或 `/login`，完成 `/setup` 首用户创建。
3. 从 v0.1.0 升级的数据库在受控网络启动后，访问同一引导并认领迁移生成的占位 owner；原有私有数据继续属于该首用户。
4. 若无法使用浏览器，停掉应用后按现有 CLI 流程设置/创建管理员；CLI 与应用不得同时打开同一个 DuckDB 文件。
5. 回滚应用代码时保留数据库文件和已创建账户；回滚不尝试逆转用户初始化，也不删除用户数据。

## Open Questions

- 是否在后续版本增加显式配置开关，允许运维完全关闭浏览器首访初始化并强制使用 CLI；本变更默认不增加该配置，以保持首次部署流程简单。
- 是否将初始化限速阈值与登录限速阈值统一为配置项；本变更先复用现有进程内限速实现，具体阈值沿用认证模块当前约定。
