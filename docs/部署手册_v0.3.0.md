# v0.3.0 部署手册（A 股历史数据）

本文对应技术方案 §77「首次真实部署步骤」与 OpenSpec 变更
`a-share-historical-data` 的 tasks 9.6，是升级到 v0.3.0 的操作手册。

文中标注 **[已演练]** 的步骤已在真实数据副本上实测通过（见文末「演练记录」）；
标注 **[待执行]** 的步骤需要真实 Tushare Token 与生产环境，由运维在部署时完成。

## 一、升级前准备

### 1. 停服

DuckDB 是单文件单写者数据库，**必须先停服再备份**，否则备份可能包含未合并的
WAL 或半写状态。

```bash
docker compose stop            # 或：停止 uvicorn / systemd 服务
```

**[已演练]** 确认停服后 `data/marketmind.duckdb.wal` 不再增长。

### 2. 备份数据库

```bash
cp data/marketmind.duckdb data/marketmind.duckdb.bak
```

**回滚方案** = 还原该备份文件 + 回退代码版本。`0003` 迁移只增不删，
但 DuckDB 不支持事务性 DDL 回滚到任意点，因此备份文件是唯一可靠的回滚手段。

### 3. 更新代码与配置

```bash
git pull
# 按 config.example.yaml 的 history 节补充 config.yaml（全部字段可省略取默认值）
```

历史同步需要有效 Tushare Token（`tushare.token`）。**未配置 Token 时同步会失败
且不推进水位，但不影响已有的行情与估值功能**。

## 二、执行迁移

容器启动时会自动执行 `alembic upgrade head`（见 `Dockerfile` 的 `CMD`），
也可手工先跑一次确认：

```bash
docker compose run --rm marketmind alembic upgrade head
```

预期输出：

```text
Running upgrade 0001_duckdb_baseline -> 0002_multi_user_auth, ...
Running upgrade 0002_multi_user_auth -> 0003_a_share_historical_data, ...
```

**[已演练]** 在真实数据的 `0001_duckdb_baseline` 副本上执行 `alembic upgrade head`：

- 迁移前 11 张表（含 `alembic_version`），`instrument` 1 行、`quote_snapshot` 1 行、
  `watchlist`/`tag` 各 1 行、`job_status` 2 行；
- 迁移后既有表的行数**逐表比对完全一致**（迁移内置行数校验）；
- 新增 11 张表（4 事实 + 3 主档 + 4 同步控制）与 `trading_calendar` 的 4 个可空列。

### 迁移影响面

- **只增不删**：新增表与索引；`trading_calendar` 增加 4 个**可空**列
  （`exchange` / `pretrade_date` / `source` / `fetched_at`，纯 `ADD COLUMN`，
  既有行留 NULL，旧写路径只写原三列，行为不变）。
- `fundamental_snapshot` 与 `FundamentalRefreshJob` **完全不动**。
- 迁移可重复执行（已应用则跳过）。

## 三、启动与验证

### 4. 启动应用

```bash
docker compose up -d
docker compose logs -f marketmind
```

**[已演练]** 启动日志确认三个 Job 均注册：

```text
INFO [app.main] 应用启动
INFO [app.jobs.quote_refresh] 行情刷新任务已启动（周期 60 秒）
INFO [app.jobs.fundamental_refresh] 估值刷新任务已启动
INFO [app.jobs.history_sync] 历史同步任务已启动（每日 20:30 Asia/Shanghai，含周末）
INFO: Application startup complete.
```

> 单 worker 是硬约束（`--workers 1`）。DuckDB 单写者，多 worker 会导致锁冲突。

### 5. 验证端点

```bash
curl -s localhost:8000/health          # {"status":"ok","database":"ok","version":"v0.3.0"}
```

**[已演练]** 权限与 CSRF（未登录/无 Token 均应被拒）：

| 请求 | 预期 |
| --- | --- |
| `GET /admin/data` 未登录 | 302 重定向登录 |
| `GET /api/admin/history-data/summary` 未登录 | 401 |
| `POST /api/admin/history-data/sync` 无 CSRF | 403 `CSRF 校验失败` |
| `POST /api/admin/history-data/sync` 带 CSRF | 202 + `run_id` |
| 运行中再次 `POST` | 409 + 当前 `run_id` |

`requested_by_user_id` 由服务端从登录态取得；**[已演练]** 确认落库值与认证用户
id 一致，客户端传入的值被忽略。

## 四、首次回填

### 6. 触发同步

管理员登录后打开 `/admin/data`，点击「检查并更新数据」；或等每日 20:30 定时任务。

```bash
# 或直接用 API
curl -X POST localhost:8000/api/admin/history-data/sync \
  -H "X-CSRF-Token: <CSRF>" -H "Content-Type: application/json"
# -> 202 {"run_id":"...","status":"RUNNING"}
```

### 7. 确认主档与进度

在 `/admin/data` 依次确认：

- **整体状态卡**：`UNINITIALIZED` → `LAGGING` → `HEALTHY`（有回填进度）；
- **主档状态表**：`trade_cal` 与 `stock_basic` 是硬前置，必须 SUCCESS，
  否则四个日级数据集本轮不执行；
- **四个日级数据集卡**：各自的 `latest_complete_trade_date` 水位独立推进；
- **当前任务 / 最近执行记录**：运行中每 4 秒轮询，结束自动停止。

### 8. 首次回填的预期行为

- **跨多次运行**：2010 年至今约 4000 个交易日 × 4 个数据集，受 Tushare 限流
  （默认 0.6 秒/请求，`stock_basic` 1.25 秒/请求）约束，不要求单次进程生命周期
  内跑完。水位即进度，下次运行从水位续跑。
- **失败停在当前水位，不跳日**：某交易日连续 10 次失败即终止该数据集本轮推进，
  记录 `failed_trade_date` 与错误码，下次从该日重试。
- **重复点击不会重复执行**：进程级 single-flight，运行中返回 409。
- **不要手工编辑历史数据或输入水位**：页面不提供该入口（设计有意为之）。

### 9. 无 Token 时的现象（部署自检）

**[已演练]** 全新库、未配置 Token 时点击同步：

```text
run:  FAILED
      error_summary: 主档硬前置失败（trade_cal/stock_basic），本轮未推进日级数据集
trade_cal:  FAILED   last_error_code=CALENDAR_UNAVAILABLE
      last_error: Tushare Token 未配置，无法获取严格交易日历（market=CN）
```

四个日级数据集保持 `UNINITIALIZED`、水位为 NULL、事实表 0 行（**未误推进**）。
错误文本不含 Token 值。

> 注意错误码取决于日历是否已缓存：全新库报 `CALENDAR_UNAVAILABLE`（`trade_cal`
> 是第一道硬前置）；若日历已缓存而 Token 事后失效，则报 `TUSHARE_TOKEN_MISSING`。
