# MarketMind A股历史数据：产品设计与数据说明

> 文档版本：v0.1  
> 文档状态：产品方案确认稿 / 技术设计输入  
> 核对日期：2026-09-16  
> 数据源：Tushare Pro  
> 历史日级数据基准起点：2010-01-01  
> 目标市场：A股全市场（按 Tushare 各接口实际覆盖范围获取）

---

## 1. 文档目的

本文档用于确定 MarketMind 新增“A股历史数据基础设施”的产品目标、数据范围、同步行为、完整性原则、后台数据管理能力及各数据集的业务含义。

本文档是下一步《技术方案设计》的输入，不在本阶段确定：

- 具体数据库表名、DDL 和索引；
- Python 类、模块、Repository / Service / Job 的具体拆分；
- API 路径和请求/响应结构；
- Alembic migration 细节；
- DuckDB SQL 实现；
- 重试库、调度库和锁的具体代码实现。

但本文档会明确技术方案必须满足的产品约束，尤其是：

1. 日级历史数据从 **2010-01-01** 开始；
2. `daily`、`adj_factor`、`daily_basic`、`moneyflow` **每个数据集都有独立的连续水位线**；
3. 水位线不能跨过失败交易日；
4. 定时更新与管理员手动更新必须复用同一套同步逻辑；
5. Tushare 能稳定获取且有分析价值的原始字段，原则上尽量完整保存；
6. 原始数据优先保存，前复权/后复权等可派生数据不重复作为事实数据存储。

---

## 2. 背景

MarketMind 当前已经以 DuckDB 作为主数据库，并在项目技术规划中预留了历史行情、`market_daily_bar`、`data_sync_state`、批量导入、增量更新、数据质量检查和未来回测等方向。

本次需求的目标不是只增加一个“下载行情”的临时脚本，而是为 MarketMind 建立一个长期可维护的历史市场数据底座，使其后续可以稳定支持：

- 股票历史 K 线；
- 前复权 / 后复权行情；
- 历史估值分析；
- 市值、股本、换手率分析；
- 资金流分析；
- 历史证券名称和公司资料展示；
- 条件选股；
- 因子研究；
- 策略研究与回测；
- AI 对股票历史数据的分析。

因此，本阶段重点是“**原始事实数据完整、连续、可观测、可恢复**”，而不是优先实现上层分析功能。

## 3. 已确认的产品决策

### 3.1 历史时间范围

日级历史数据统一从：

```text
2010-01-01
```

开始。

实际同步时以 A 股交易日历为准，因此不会把周末、法定节假日等休市日期当作需要获取行情的日期。

### 3.2 日级核心数据集

第一阶段确认同步并长期保存以下四个日级数据集：

| 数据集 | Tushare 接口 | 作用 | 连续水位线 |
|---|---|---|---|
| 日线行情 | `daily` | OHLC、成交量、成交额等原始未复权行情 | 是 |
| 复权因子 | `adj_factor` | 前复权/后复权计算基础 | 是 |
| 每日指标 | `daily_basic` | PE、PB、PS、换手率、股本、市值等 | 是 |
| 个股资金流 | `moneyflow` | 小/中/大/特大单及净流入数据 | 是 |

四个数据集分别维护自己的同步进度。

例如：

```text
daily          latest_complete_trade_date = 2026-09-15
adj_factor     latest_complete_trade_date = 2026-09-16
daily_basic    latest_complete_trade_date = 2026-09-15
moneyflow      latest_complete_trade_date = 2026-09-12
```

某个数据集失败，不允许该数据集越过失败日期继续前进；其他数据集可以按照自己的连续水位线继续同步。

### 3.3 基础与主档数据集

同时保存：

| 数据集 | Tushare 接口 | 作用 |
|---|---|---|
| 股票基础信息 | `stock_basic` | 股票代码、名称、市场、上市/退市状态等证券主档 |
| 交易日历 | `trade_cal` | 决定哪些日期属于应处理交易日 |
| 股票曾用名 | `namechange` | 保存股票历史名称及变更原因 |
| 上市公司基本信息 | `stock_company` | 公司名称、注册信息、管理层、主营业务等 |

这些数据同样独立维护同步状态，但它们不是“每天必有一条记录”的交易日序列，因此不人为制造交易日水位线：

- 日级历史数据：使用“连续交易日水位线”；
- 主档/事件数据：使用“最近成功刷新状态”。

### 3.4 原始数据优先

MarketMind 保存原始事实数据，不以 `pro_bar` 产生的动态复权价格作为历史事实表的主数据。

长期保存：

```text
原始 daily
+
adj_factor
```

需要前复权或后复权时再计算。

原因：

- 原始行情不会因为复权基准变化而变化；
- 前复权价格与选定的最新复权因子相关；
- 同一份原始行情可同时支持 raw / qfq / hfq；
- 避免保存三套高度重复的数据。

## 4. 产品范围

### 4.1 第一阶段包含

第一阶段包含以下产品能力：

1. 从 Tushare 获取 A 股历史日级数据；
2. 日级历史起点为 2010-01-01；
3. 首次运行尝试从起点一路同步至当前可用最新交易日；
4. 后续每天自动更新；
5. 每次执行强制根据各数据集连续水位线追平；
6. 任何日期失败不得跳过；
7. 单次任务内失败最多尝试 10 次；
8. 10 次仍失败时停止该数据集本次推进；
9. 下一次执行自动从失败日期继续；
10. 重复执行必须安全，不产生重复事实记录；
11. 管理员后台增加“数据管理”页面；
12. 管理员可以查看数据覆盖、同步进度、失败状态和执行记录；
13. 管理员可以手动触发与定时任务完全相同的数据检查与更新；
14. 保存 Tushare 当前接口能够提供且有分析价值的完整原始字段；
15. 包含退市股票等历史证券身份数据。

### 4.2 第一阶段不包含

第一阶段暂不包含：

- 分钟行情；
- Tick 数据；
- 实时逐笔数据；
- ETF / 指数历史行情体系；
- 财务三大报表历史库；
- 回测引擎；
- 因子计算引擎；
- 预计算技术指标库；
- 在数据库中重复存储前复权、后复权 K 线；
- 管理员直接修改或删除历史行情数据。

这些能力后续可以建立在本次历史数据底座之上。

# 5. 数据体系总览

建议从产品概念上把数据分为四层。

```text
┌─────────────────────────────────────┐
│ 证券与公司主档                       │
│ stock_basic / stock_company /       │
│ namechange                          │
└──────────────────┬──────────────────┘
                   │
┌──────────────────▼──────────────────┐
│ 市场时间轴                           │
│ trade_cal                           │
└──────────────────┬──────────────────┘
                   │
┌──────────────────▼──────────────────┐
│ 日级市场事实数据                     │
│ daily / adj_factor / daily_basic /  │
│ moneyflow                           │
└──────────────────┬──────────────────┘
                   │
┌──────────────────▼──────────────────┐
│ 同步控制与数据健康                   │
│ 水位线 / 状态 / 执行记录 / 错误记录 │
└─────────────────────────────────────┘
```

核心原则是：

> `trade_cal` 决定时间轴，证券主档决定“谁”，日级事实数据描述“发生了什么”，同步控制层保证“没有跳着往前走”。

# 6. 数据集详细说明

## 6.1 股票基础信息 `stock_basic`

### 产品定位

证券主档。

需要覆盖当前上市股票，也需要纳入退市、暂停上市以及 Tushare 能提供的其他上市状态，避免历史行情中出现“只有代码但没有证券身份”的孤立记录。

日级历史数据从 2010 年开始，但证券主档不需要裁剪到 2010 年；只要 Tushare 能获取，就完整保存当前接口提供的信息。

- 不只请求默认的 `L`（上市）状态；
- 应覆盖 Tushare 当前可提供的上市状态；

### 后续价值

## 6.2 交易日历 `trade_cal`

### 产品定位

历史同步系统的统一时间轴。

Tushare 文档说明 A 股三大交易所交易日历一致，因此产品逻辑上可以使用统一的 A 股交易日历判断：

- 哪些日期应该执行日级同步；
- 当前最近一个有效交易日；
- 水位线的“下一交易日”是什么；
- 当前数据落后多少个交易日。

### 建议保存全部当前输出字段

| 字段 | 含义 |
|---|---|
| `exchange` | 交易所 |
| `cal_date` | 日历日期 |
| `is_open` | 是否交易：0 休市，1 交易 |
| `pretrade_date` | 上一个交易日 |

### 产品要求

不能通过简单的：

```text
date + 1
```

推进历史同步。

必须依据交易日历推进：

```text
latest_complete_trade_date
        ↓
查询下一个 is_open = 1 的日期
        ↓
同步
        ↓
成功后水位线推进
```

# 7. 核心日级历史数据

## 7.1 A股日线行情 `daily`

### 产品定位

这是整个历史市场数据库最核心的事实数据。

Tushare `daily` 是未复权行情，且官方明确说明停牌期间不提供日线记录。

全市场历史同步应优先按照“交易日期”获取，而不是按股票逐只循环。

### 历史范围

```text
2010-01-01 → 当前可用最新交易日
```

### 建议保存全部当前输出字段

| 字段 | 含义 | 单位/备注 |
|---|---|---|
| `ts_code` | 股票代码 | |
| `trade_date` | 交易日期 | |
| `open` | 开盘价 | |
| `high` | 最高价 | |
| `low` | 最低价 | |
| `close` | 收盘价 | |
| `pre_close` | 昨收价（除权价） | |
| `change` | 涨跌额 | |
| `pct_chg` | 涨跌幅 | % |
| `vol` | 成交量 | 手 |
| `amount` | 成交额 | 千元 |
| `ah_vol` | 盘后成交量 | 手 |
| `ah_amount` | 盘后成交额 | 千元 |

### 特殊说明

Tushare 当前文档说明：

- `daily` 为未复权行情；
- 停牌期间没有日线记录；
- `ah_vol`、`ah_amount` 从 2026-07-06 开始才有数据。

因此：

- 2010～2026-07-05 的 `ah_vol / ah_amount` 为空属于正常情况；
- 某只已上市股票在某个交易日没有 `daily` 行，不能仅据此判定数据库有缺口；
- 数据完整性的核心首先是“交易日期请求没有被跳过”，然后再做单日返回结果质量检查。

## 7.2 复权因子 `adj_factor`

### 产品定位

保存原始复权因子，为前复权、后复权价格计算提供基础。

### 历史范围

```text
2010-01-01 → 当前可用最新交易日
```

### 建议保存全部当前输出字段

| 字段 | 含义 |
|---|---|
| `ts_code` | 股票代码 |
| `trade_date` | 交易日期 |
| `adj_factor` | 复权因子 |

### 产品原则

数据库不需要另外长期保存三份：

```text
raw
qfq
hfq
```

只需长期保存：

```text
raw daily + adj_factor
```

根据 Tushare 当前说明：

```text
后复权价格 ≈ 原始价格 × 当日复权因子
```

前复权需要相对于选定终点/最新日期的复权因子进行归一化，因此属于派生结果，不适合作为唯一事实数据长期固化。

Tushare 当前分类规则为：

- 大单：20 万～100 万；
- 特大单：成交额 ≥ 100 万。

同时，Tushare 明确指出 `net_mf_*` 是基于主动买卖单及 L2 订单计算的净值，不能简单用大小单字段自行相减替代。因此应保留官方原始净流入字段。

---

# 8. `pro_bar` 的产品定位

`pro_bar` 不作为本阶段独立事实数据集入库。

原因：

1. 它是 SDK 层集成接口；
2. 单次主要围绕单一证券使用，不适合作为全市场按日期同步的底层接口；
3. 前复权、后复权数据依赖复权因子动态计算；
4. 均线等部分指标属于动态计算结果；
5. 长期保存会与 `daily + adj_factor` 产生大量重复。

MarketMind 可以在未来的数据访问/分析层复用相同算法生成：

- raw；
- qfq；
- hfq；
- MA 等技术指标。

因此，`pro_bar` 在本产品中的定位是：

> **算法和使用方式参考接口，而不是新的原始数据事实表。**

---

# 9. “尽量完整保存”的字段策略

本阶段确定以下原则。

## 9.1 不只保存 Tushare 默认字段

如果接口存在“默认不返回但可通过 `fields` 获取”的字段，也应主动获取。

典型包括：

- `stock_basic.fullname`
- `stock_basic.enname`
- `stock_basic.exchange`
- `stock_basic.curr_type`
- `stock_basic.list_status`
- `stock_basic.delist_date`
- `stock_basic.is_hs`
- `stock_company.introduction`
- `stock_company.office`
- `stock_company.main_business`
- `stock_company.business_scope`
- `daily.ah_vol`
- `daily.ah_amount`
- `daily_basic.limit_status`

目标是：

> 只要当前权限能够获取、字段具有明确语义且保存成本合理，就优先保留原始值，避免以后需要重新拉十几年历史。

## 9.2 原始单位保持不变

事实层优先保持 Tushare 官方单位，不在入库阶段随意换算。

例如：

- `daily.vol`：手；
- `daily.amount`：千元；
- `daily_basic.total_mv`：万元；
- `moneyflow.*_amount`：万元。

后续展示或分析需要“元”“亿元”等单位时，在查询/服务/展示层转换。

## 9.3 上游 NULL 原样保存

不为了“看起来完整”而人工填充：

- PE 亏损导致的 NULL；
- 尚未产生的数据字段；
- 历史阶段不存在的新字段；
- 公司资料中的可选字段。

NULL 本身也是事实语义。

## 9.4 增加内部采集元数据

虽然具体字段名由技术方案确定，但每类数据应能够追踪至少：

- 数据来源（Tushare）；
- 获取时间；
- 所属同步执行；
- 必要时的数据版本/更新时间信息。

这些字段服务于审计、排错和未来多数据源扩展，不替代 Tushare 原始业务字段。

# 10. 连续水位线模型

这是本产品最重要的数据完整性原则。

## 10.1 定义

对于：

- `daily`
- `adj_factor`
- `daily_basic`
- `moneyflow`

每个数据集独立维护：

```text
latest_complete_trade_date
```

它的含义不是：

> 数据库里最大的日期。

而是：

> 从历史起点开始，所有应该处理的交易日已经连续、按顺序完成到哪一天。

### 示例

假设：

```text
历史起点：2010-01-01
daily 水位：2025-09-01
当前目标：2026-09-16
```

本次执行必须处理：

```text
2025-09-02
2025-09-03
...
2026-09-16
```

中间任何应处理交易日都不可跳过。

如果 2025-11-07 在第 10 次尝试后仍失败：

```text
daily 水位只能停留在 2025-11-06
```

不得继续获取并把：

```text
2025-11-10
2025-11-11
...
```

标记为完成。

下一次任务仍然从：

```text
2025-11-07
```

开始。

---

## 10.2 “最大日期”不能替代水位线

数据库中存在一条较晚日期记录，并不代表此前所有日期完整。

因此：

```text
MAX(trade_date)
```

只能作为辅助校验，不是唯一同步游标。

技术方案必须以“最后连续完成交易日”作为推进依据。

---

## 10.3 水位线只能在完整成功后推进

对某数据集的某个交易日：

```text
拉取
  ↓
校验
  ↓
写入
  ↓
确认成功
  ↓
推进 latest_complete_trade_date
```

顺序不可反过来。

不能出现：

```text
先把水位线改成今天
↓
再慢慢写数据
```

否则中途失败会制造永久缺口。

---

# 11. 单日完整性的产品定义

“连续日期”解决的是时间轴缺口，但还需要避免一次 API 返回异常或截断的数据被误认为成功。

## 11.1 必须通过的基础检查

一个数据集的某个交易日至少应满足：

1. Tushare 请求明确成功；
2. 返回结构符合预期；
3. 主键性字段存在；
4. 返回记录中的 `trade_date` 与请求日期一致；
5. 同一业务唯一键不能出现非预期重复；
6. 写入过程成功完成；
7. 不存在明显的异常截断信号；
8. 只有通过检查后才推进水位线。

## 11.2 不能简单用“上市股票数量”判断 `daily`

`daily` 官方明确说明：

> 停牌期间不提供行情数据。

因此不能做：

```text
当日上市股票 = 5300
daily 返回 5250
→ 判定缺 50 条
```

这会把正常停牌误判成数据缺失。

单日证券级完整性要按各数据集自身语义判断。

## 11.3 API 上限必须视为风险信号

`daily`、`daily_basic`、`moneyflow` 当前文档均存在单次最多返回 6000 行的限制。

因此，如果未来某个交易日请求结果恰好达到接口最大返回量：

```text
row_count == 6000
```

不能直接认为“完整”。

产品要求技术方案能够识别潜在截断，并在不能确认完整时：

> **不推进该数据集水位线。**

具体如何拆分请求、二次验证，由下一步技术设计确定。

## 11.4 空结果的处理

交易日出现完全空结果时，不能默认标记成功。

应区分：

- 上游数据尚未更新；
- 权限/限流问题；
- 网络/API 异常；
- 接口自然无覆盖；
- 真正合理的空数据。

无法确认合理性时不推进水位线。

---

# 12. 首次同步行为

## 12.1 首次运行

如果日级数据集没有水位线：

```text
start_date = 2010-01-01
```

通过 `trade_cal` 找到从该日期起的实际交易日，然后从旧到新顺序处理。

概念流程：

```text
准备证券主档
    ↓
准备交易日历
    ↓
daily        从 2010 开始追平
adj_factor   从 2010 开始追平
daily_basic  从 2010 开始追平
moneyflow    从 2010 开始追平
    ↓
记录各自独立水位线
```

产品层不人为设置“只补最近 N 天”的截断。

第一次执行应尽可能尝试一路追平到最新可用交易日。

如果受 Tushare 限流、权限、网络或数据错误影响，按失败策略停止对应数据集，并在下一次继续。

---

# 13. 日常增量同步行为

以后每天执行时，不采用“只抓今天”的逻辑。

每个数据集都执行：

```text
读取 latest_complete_trade_date
        ↓
根据 trade_cal 找到下一交易日
        ↓
一直列出到 latest_expected_trade_date
        ↓
按顺序逐日处理
        ↓
每成功一天推进一天
```

因此，即使服务器停机一年：

```text
数据库水位：2025-09-01
恢复运行：2026-09-16
```

脚本也必须尝试完整处理：

```text
2025-09-02 → 2026-09-16
```

而不是直接跳到 2026-09-16。

这条规则是硬性产品约束。

---

# 14. “当前最新数据”的定义

不能单纯把服务器当天日期作为所有数据集目标，因为：

- 今天可能是休市日；
- 今天可能尚未收盘；
- 不同 Tushare 数据集更新时间不同；
- 管理员可能在盘中手动点击更新。

因此每个日级数据集还需要计算自己的：

```text
latest_expected_trade_date
```

它代表：

> 按当前交易日历和上游发布时间，此刻理论上应该已经可获得的最新交易日。

例如管理员上午手动更新时：

- 不应因为当天收盘行情尚未生成而把任务错误标记为失败；
- 系统应提示“已同步到当前可用最新交易日”。

统一的每日定时任务建议安排在中国市场晚间、主要日级数据已更新之后执行，并且明确使用：

```text
Asia/Shanghai
```

作为市场时间基准，避免服务器部署在其他时区时产生日期错误。

具体执行时刻在技术设计中最终确定。

---

# 15. 失败重试策略

用户需求确认：

```text
同一数据集、同一应处理日期
单次任务最多尝试 10 次
```

产品要求：

1. 失败不能立即无间隔连续打满 10 次；
2. 重试间隔应逐步拉长；
3. 建议加入少量随机抖动，避免持续撞上限流窗口；
4. 总尝试次数达到 10 次仍失败时，停止该数据集本次同步；
5. 不跳过当前失败日期；
6. 不无限重试；
7. 下一次定时或手动执行，从该失败日期继续；
8. 管理员页面必须能看到失败日期、尝试次数和最后错误。

具体秒数由技术方案确定。

---

# 16. 多数据集失败关系

由于四个日级数据集具有独立水位线：

- `daily` 失败，不强制阻止 `adj_factor` 推进；
- `moneyflow` 失败，不强制让 `daily` 回退；
- 每个数据集只对自己的连续性负责。

统一同步任务可以出现：

```text
daily         成功追平
adj_factor    成功追平
daily_basic   成功追平
moneyflow     停在某日失败
```

此时整次任务的产品状态应表现为：

```text
部分成功 / 存在数据集未追平
```

而不是掩盖失败，也不是把已经成功的数据回滚。

---

# 17. 幂等与重复执行要求

无论是：

- 自动任务重复触发；
- 管理员重复点击；
- 进程异常退出后重新执行；
- 网络超时导致无法确定上一请求状态；

都不能产生重复历史事实记录。

产品要求：

> 同一个证券、同一个交易日、同一个数据集的数据重复同步必须是安全操作。

具体唯一键、UPSERT 或批量覆盖方式由技术方案确定。

---

# 18. 统一同步入口

本产品不接受两套同步逻辑：

```text
cron 一套逻辑
+
管理员按钮另一套逻辑
```

必须只有一个统一的历史数据同步能力。

触发来源可以不同：

```text
定时任务 ─┐
          ├──> Historical Data Sync
管理员按钮 ┘
```

但最终执行：

- 数据检查；
- 计算目标日期；
- 读取水位线；
- 按顺序补数据；
- 校验；
- 写入；
- 重试；
- 更新状态；

必须是同一套流程。

这样可以避免：

> 自动任务正常，手动按钮却使用另一套规则把数据弄乱。

# 19. 管理员“数据管理”页面

## 19.1 页面定位

管理员页面不是历史行情查询器，而是：

> **历史数据健康与同步控制台。**

1. 有哪些数据集；
2. 每个数据集从哪里开始；

# 20. 数据状态建议

日级数据集至少需要表达以下状态语义：

| 状态 | 含义 |
|---|---|
| 未初始化 | 从未执行过历史同步 |
| 检查中 | 正在计算当前目标和待处理日期 |
| 同步中 | 正在正常获取/写入 |
| 重试中 | 当前日期发生临时失败，尚未用完 10 次机会 |
| 已追平 | 水位线达到当前可用目标日期 |
| 落后 | 已知存在待同步交易日 |
| 失败 | 10 次尝试后当前日期仍未完成 |
| 等待数据源 | 当日理论交易但当前接口尚未到发布时间 |

具体数据库枚举名由技术方案决定。

# 21. 数据完整性的三层定义

为了避免以后“完整”一词含义混乱，本产品把完整性分成三层。

## 21.1 时间连续性

从 2010 起到当前水位之间不存在任何被跳过的应处理交易日。

这是最强硬的约束。

## 21.2 单日请求完整性

该交易日的数据请求：

- 成功；
- 未明显截断；
- 结构合法；
- 可安全写入；
- 通过数据集自身的校验规则。

否则不能推进水位。

## 21.3 证券级自然缺失

上游规则导致某个证券当天本来就没有数据，例如：

- 停牌导致 `daily` 无记录；
- 某数据集不覆盖某证券/市场；
- 某字段在历史阶段尚不存在。

这些情况不等于同步日期缺失。

# 22. 数据源权限与流量约束

当前用户 Tushare 积分：

```text
2000
```

已确认的主要接口要求中：

- `stock_basic`：2000 积分起；
- `trade_cal`：2000 积分；
- `adj_factor`：2000 积分起；
- `daily_basic`：2000 积分起；
- `moneyflow`：2000 积分起；
- `stock_company`：120 积分起；
- `daily`：当前文档允许基础积分调用，并有单次/分钟限制。

需要注意：

- `daily_basic` 当前文档特别注明 5000 积分“无总量限制”；
- `adj_factor` 当前文档注明 5000 以上可高频调取；
- 多个接口存在每次最多返回 6000 行限制。

因此技术方案必须把：

- 限流；
- 请求节奏；
- 10 次重试；
- 潜在总量限制；
- 长历史首次回填；

作为正式设计问题，而不能依赖高并发暴力抓取。

# 23. 与 MarketMind 现有产品/架构的关系

MarketMind 当前技术规划已经明确：

- DuckDB 作为主数据库；
- 单应用进程写数据库；
- 历史行情与最新行情分离；
- 使用轻量写协调机制统一数据库写操作；
- 未来增加历史行情事实表和同步状态；
- 历史行情阶段需要批量导入、增量更新、去重和数据质量检查；
- 原始 OHLC 和 `adj_factor` 应保留，复权结果按需计算。

因此，本产品设计不要求引入另一套独立数据库，也不要求为了历史行情单独引入复杂消息队列。

具体如何复用 MarketMind 当前的：

- Provider；
- Repository；
- Service；
- Jobs；
- WriteCoordinator；
- JobStatus；
- Admin；

由下一步技术方案确定。

# 24. 第一阶段验收标准

产品层面至少满足以下条件才算完成。

## 24.1 数据

# 26. 本阶段最终结论

MarketMind 的历史数据功能第一阶段定位为：

> **从 2010 年开始，建立一份能够自行追平、不会跳过失败交易日、可由管理员观测和手动触发的 A 股历史原始数据底座。**

数据底座由以下内容组成：

```text
证券主档
stock_basic
stock_company
namechange

市场时间轴
trade_cal

日级历史事实
daily
adj_factor
daily_basic
moneyflow

同步控制
每个日级数据集独立连续水位线
+
同步状态
+
执行记录
+
错误信息
```

其中最重要的约束是：

> **日级数据水位只能连续向前推进。某一天没有成功，下一天就不能被该数据集标记为完成。**

同时：

> **原始数据尽量完整保留，动态计算结果尽量不重复固化。**

这套产品边界完成后，可以稳定作为下一阶段技术方案、历史 K 线、历史估值、选股、因子分析与回测能力的基础。
