# v0.4.0 性能基准测试报告

## 测试目标

验证 v0.4.0 个股区间替换机制的批量写入性能，确保实现未退化为"逐行 ORM / 每行一次 commit"。

**设计依据**: 
- 技术方案 a-share-historical-data §74
- OpenSpec per-stock-history-sync Design D14

## 测试方法

### 基准策略

使用**相对加速比**而非绝对毫秒 SLA：
- 同机实测逐行写入基线（500 行样本外推）
- 批量路径须显著快于逐行基线（≥5× 加速）
- 相对比值不受机器性能与负载漂移影响，可复现性强

### 写入路径

真实生产路径：`app/repositories/history_fact.py`
- 注册 DuckDB 临时视图（Pandas DataFrame）
- `INSERT INTO ... SELECT * FROM temp_view`
- 实测相对 `executemany` 快约 14×

### 测试场景

#### 场景 1：整日替换（历史机制对照）

**目的**: 验证 v0.3.1 日级同步机制性能基线

**规模**:
- 2 个数据集 × 100 个交易日 = 200 次整日替换
- 每日 6000 行（模拟 5000 只股票 × 多指标数据集）
- 总计 120 万行

**操作流程**:
- 逐日"整日 DELETE + 批量 INSERT + 水位状态更新"
- 抽查事实表基础 date filter 读取路径

**断言**:
- 提交次数 = 数据集数 × 交易日数（不随行数增长）
- SQL 语句总数 << 总行数（证明非逐行 INSERT）
- 批量写入加速比 ≥ 5× 逐行基线

#### 场景 2：个股区间替换（v0.4.0 生产路径）

**目的**: 验证个股同步执行器 `StockSyncExecutor` 性能

**规模**:
- 20 只股票 × 每股 4000 行（16 年历史量级）
- 总计 8 万行

**操作流程**:
- 真实 `StockSyncExecutor` 实例
- Fake registry 锁外返回合成批次
- 三事务模式：①task 创建 running → ②fetch/validate → ③原子提交（replace_for_instrument_range + advance_watermark + finish_success + add_counts）

**断言**:
- 提交次数 = 2 × 股数（task 创建 + 成功提交，不随行数增长）
- SQL 语句总数 << 总行数
- 批量写入加速比 ≥ 5× 逐行基线

## 性能分析

### 事务优化效果

**场景 1（整日）**:
- 提交次数固定为 200，与 120 万行数无关
- 每次提交包含约 6000 行批量 INSERT
- 证明无"逐行 commit"退化

**场景 2（个股）**:
- 提交次数固定为 40（2×20 股），与 8 万行数无关
- 三事务模式下每股仅 2 次提交（task 创建 + 原子提交）
- 证明 `StockSyncExecutor` 事务边界设计正确

### SQL 优化效果

**场景 1**:
- SQL 语句总数 1,737 条 < 总行数 1,200,000 的 0.14%
- 平均每日 8.69 条 SQL（DELETE + INSERT + UPDATE state）

**场景 2**:
- SQL 语句总数 241 条 < 总行数 80,000 的 0.30%
- 平均每股 12.05 条 SQL（task CRUD + watermark + fact replace）

### 批量写入加速比

**场景 1**: 57.0× 加速
- 逐行基线：4.69 毫秒/行 → 批量：0.082 毫秒/行
- 视图 + INSERT SELECT 模式效率极高

**场景 2**: 36.2× 加速
- 单股约 4000 行一次性提交
- 相比场景 1 略低（0.130 vs 0.082 毫秒/行）可能因单股行数较少（4000 vs 6000）、固定开销占比略高

## 性能基线建议

### 回归测试阈值

为防止未来代码变更引入性能退化，建议设定以下回归阈值：

**提交次数**:
- 场景 1: 必须 = 数据集数 × 交易日数（严格相等）
- 场景 2: 必须 = 2 × 股数（严格相等）

**SQL 语句数**:
- 必须 < 总行数的 1/100（两个场景均 < 0.5%）

**加速比**:
- 必须 ≥ 5× 逐行基线（两个场景均 > 30×，安全边际充足）

### 吞吐量参考

在当前测试环境下：
- 整日替换：**11,618 行/秒**（986 毫秒/日，6000 行）
- 个股替换：**7,722 行/秒**（517 毫秒/股，4000 行）

**生产环境预估**（5000 只股票、16 年历史、4 个数据集）:
- 单股单数据集约 4000 行
- 全量回填：5000 股 × 4 数据集 = 20,000 个任务
- 按 7,722 行/秒吞吐：20,000 任务 × 4000 行 ÷ 7,722 行/秒 ≈ **2.87 小时**（纯写入时间）
- 实际包含网络请求、重试、调度间隙，预计 **8-12 小时内完成**（分多轮运行）

## 结论

✅ **v0.4.0 个股区间替换机制性能验证通过**

1. **无事务退化**: 提交次数与行数解耦，严格控制在"数据集×交易日"或"2×股数"
2. **无逐行 INSERT**: SQL 语句数远小于行数（< 0.5%）
3. **批量写入高效**: 相对逐行基线加速 36-57×，远超 5× 要求
4. **生产可行性**: 全量回填预计 8-12 小时，分多轮自动完成，符合设计预期

**回归保护**: 已在 `scripts/bench/bench_history_write.py` 内置 6 项断言，任何性能退化将导致基准测试失败（退出码 1）。
